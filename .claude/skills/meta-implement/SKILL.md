# meta-implement

잠긴 테스트를 통과하도록 구현한다.
독립성이 확인된 레인만 병렬로 구현하고, 이 스킬이 통합 담당으로서 레인을 하나씩 합친다.
합친 뒤에는 우리 모듈끼리의 mock을 걷어내고 진짜로 맞는지 항상 확인한다.
외부 서비스는 가짜로 두고, API 키만 넣으면 진짜로 돌 수 있게 준비한다.

## 순서

1. 읽기
   ai/tasks.md, ai/plan.md, ai/research.md를 읽는다.
   잠금 태그 lock/002-signup이 있는지 확인한다. 없으면 멈추고 /meta-tdd를 먼저 하라고 알린다.
   tasks.md의 레인, 공용 파일, 묶음(병렬, 순차)을 확인한다.

2. 병렬 묶음 구현 (3단계)
   병렬 묶음의 레인마다 meta-implementer 에이전트를 띄운다. 이 에이전트는 별도 작업 폴더(worktree)에서 일한다.
   동시에 최대 4개. 하나가 끝나면 다음 레인을 시작한다.
   각 에이전트에게 넘길 것
   - 레인 이름과 그 레인의 작업
   - 맡은 파일 목록
   - 그 레인의 테스트 파일
   - plan.md의 인터페이스와 research.md의 사용법
   에이전트는 자기 레인 브랜치에 커밋하고, 브랜치 이름과 테스트 결과를 돌려준다.

   공용 파일을 고쳐야 한다고 돌려준 레인은 순차 묶음으로 옮긴다. 그 레인의 작업은 버리지 않는다.

3. 레인 확인 (합치기 전)
   레인 브랜치마다 확인한다.
   - 테스트: git diff lock/002-signup..레인브랜치 -- 테스트파일 이 비어 있어야 한다
   - 파일: git diff lock/002-signup..레인브랜치 --name-only 가 모두 그 레인이 맡은 파일이어야 한다
   어긋나면 그 레인에 다시 맡긴다.
   설치가 필요하다고 돌려준 레인이 있으면, 그 라이브러리가 tech.md에 있을 때만 스킬이 spec 브랜치에 설치하고 그 레인을 다시 맡긴다.
   tech.md에 없으면 멈추고 /meta-tech로 돌아가자고 알린다.

4. 통합 (4단계, 스킬이 통합 담당)
   spec 브랜치에 레인 브랜치를 하나씩 합친다. tasks.md의 레인 순서대로 합친다.

   충돌이 없으면
   - 그 레인의 테스트와 typecheck를 실행한다. 통과하면 다음 레인으로

   충돌이 나면 양쪽 변경과 두 레인의 작업 목록을 읽고 나눈다.
   단순 충돌: 통합 담당이 직접 해결한다
   - 양쪽이 서로 다른 줄을 추가했을 뿐이다. 예: import 줄, 목록에 항목 추가
   - 공용 파일에 각자 자기 것을 등록했다
   - 해결 방법이 "둘 다 남긴다"로 끝난다
   설계 충돌: 그 레인 담당에게 맡긴다
   - 같은 함수의 동작을 양쪽이 다르게 바꿨다
   - 인터페이스나 공용 타입을 한쪽이 바꿨다
   - 둘 다 남기면 동작이 달라진다
   애매하면 설계 충돌로 본다.

   설계 충돌이면
   - 합치기를 취소한다
   - 그 레인의 meta-implementer에게 "충돌 수정"을 맡긴다. 지금까지 합쳐진 spec 브랜치를 자기 레인 브랜치에 합치고, 자기 레인의 목표대로 충돌을 고치고, 자기 레인 테스트를 통과시킨 뒤 커밋한다
   - 3번 레인 확인을 다시 하고 다시 합친다

   해결한 뒤에는 관련 레인의 테스트와 typecheck를 실행한다.
   레인 하나를 합칠 때마다 tasks.md에 "통합 완료: {레인}"을 체크한다.

5. 순차 묶음 구현
   순차 묶음의 레인을 하나씩 처리한다.
   지금까지 합쳐진 spec 브랜치에서 meta-implementer를 띄우고, 끝나면 3번과 4번처럼 확인하고 합친다.
   앞 레인을 합친 뒤에 다음 레인을 띄운다.

6. 공용 파일 마무리
   tasks.md에서 통합 단계에 고치기로 한 공용 파일을 스킬이 고친다.

7. 이번 기능 확인
   모든 레인을 합친 뒤 한 번에 실행한다.
   - test: 이번 기능의 단위 테스트가 모두 통과해야 한다
   - typecheck: 레인 구현끼리 인터페이스가 맞아야 한다
   - lint: 자동 수정을 먼저 돌리고, 남은 오류만 고친다. 경고는 막지 않는다
   실패하면 src/ 코드를 고친다. 잠긴 테스트는 고치지 않는다.

8. 외부 서비스 준비
   가짜 응답
   - research.md에 있는 최신 문서의 실제 응답 예시로 만든다. 지어내지 않는다.
   - 성공과 오류 응답을 모두 만든다.
   - 예시가 research.md에 없으면 meta-researcher 에이전트에게 찾게 한다.
   - 가짜 응답은 테스트 도구가 네트워크 요청을 가로채서 돌려준다. 예: MSW
   - 앱 코드는 항상 진짜 외부 서비스를 부른다. 가짜와 진짜를 고르는 분기는 테스트 도구가 맡는다.
   실제 연동 테스트
   - 외부 서비스마다 파일 하나로 둔다. 예: tests/live/supabase.live.test.ts
   - 이번 기능이 새로 쓰는 외부 호출만 그 파일에 추가한다.
   - 실제 응답이 가짜 응답과 모양이 같은지도 확인한다.
   - 파일 맨 위에서 필요한 환경 변수가 없으면 전체를 건너뛰게 만든다. 실패가 아니라 건너뜀이다.
   - 평소 테스트 실행에서는 빠지게 설정한다. 실행은 /meta-live가 한다.
   키 준비
   - 코드는 API 키를 환경 변수에서 읽는다.
   - 필요한 환경 변수 이름을 .env.example에 값 없이 적는다.
   환경 변수 검사
   - 환경 변수는 env 모듈 한 곳에서 읽는다. 예: src/lib/env.ts
   - env 모듈이 없으면 만든다. 있으면 이번 기능의 변수 이름만 추가한다.
   - 앱이 시작할 때 필요한 변수를 모두 검사한다.
   - 빠진 변수가 있으면 이름을 모두 모아 한 번에 알리고 멈춘다.
     예: 환경 변수가 없습니다: SUPABASE_URL, TOSS_SECRET_KEY
         .env.example을 참고해 .env에 넣어 주세요.
   - 환경 변수를 env 모듈에서 읽는지 확인하는 린트 규칙을 켠다. meta-wiki가 이것을 architecture.md 구조 규칙에 적는다.

9. 통합 테스트
   plan.md 8번의 통합 시나리오마다 통합 테스트를 쓴다. 이번 기능의 시나리오만 쓴다.
   테스트 이름은 기능 번호와 SC 번호로 시작한다. 예: "002/SC-003 가입 버튼을 누르면 0.5초 안에 결과가 나온다"
   우리 모듈끼리는 진짜를 연결한다. 외부 서비스는 8번의 가짜 응답으로 대신한다.
   실패하면 src/ 코드를 고친다. 잠긴 테스트는 그대로 둔다.
   응답 시간
   - 시간 기준이 있는 시나리오는 실제로 시간을 재고 기준을 넘으면 실패시킨다.
   - 첫 실행은 버리고 여러 번 돌린 평균으로 잰다. 컴퓨터마다 차이가 있기 때문이다.
   - 외부 서비스가 가짜라서 재는 시간은 우리 코드의 시간이다.
   - 기준을 넘으면 어디서 시간이 걸리는지 재서 원인을 찾고 코드를 고친다.
     예: 반복문 안의 DB 호출, 필요 없는 전체 읽기, 기다릴 필요 없는 순차 호출
   - 코드를 고쳐도 기준을 지킬 수 없으면 멈추고 사용자에게 묻는다. spec의 기준을 바꿀지 정해야 한다.

10. 회귀 테스트
   프로젝트 전체에 test, typecheck, lint를 실행한다. tests/live/는 뺀다.
   이전 기능의 테스트가 실패하면 이번 코드가 이전 기능을 깨뜨린 것이다.
   - src/ 코드를 고친다. 이전 기능의 테스트는 그대로 둔다.
   - 이번 spec이 이전 기능의 동작을 일부러 바꾸는 경우라면 멈추고 사용자에게 묻는다.
     어느 spec의 무엇이 충돌하는지 보여준다.
   - 사용자가 허락하면 순서대로 고친다.
     1. 이전 기능의 spec.md를 최신 동작으로 고친다
     2. 그 spec에 맞게 이전 기능의 테스트를 고친다
     3. 코드를 고치고 회귀 테스트를 다시 돌린다
     4. 커밋 메시지에 어느 spec의 무엇을 왜 바꿨는지 쓴다
     5. 이전 기능의 wiki를 위해 /meta-wiki를 다시 돌리라고 알린다

11. 막혔을 때
   한 레인이 두 번 다시 맡겨도 통과하지 못하면 멈춘다.
   같은 레인이 설계 충돌로 두 번 연속 돌아오면 멈춘다.
   테스트가 틀렸다는 보고가 오면 사용자에게 보여주고 판단을 받는다.
   인터페이스를 바꿔야 한다는 보고가 오면 멈추고 /meta-plan으로 돌아가자고 알린다.

12. 커밋과 정리
   커밋 메시지: "feat: 002-signup 구현"
   다 합친 레인의 작업 폴더와 레인 브랜치를 지운다.

13. 마무리
   tasks.md의 3~4단계 작업에 체크한다.
   spec-index.md 상태를 "implement 완료"로 바꾸고 커밋한다.
   다음 단계는 /meta-converge라고 알린다.

## 수렴 회차일 때

tasks.md 5단계에 체크 안 된 "수렴 추가 (N회차)" 할 일이 있으면 그 할 일만 처리한다.

1. 잠금 태그는 lock/002-signup-rN을 쓴다. 없으면 /meta-tdd를 먼저 하라고 알린다.
2. 할 일의 레인 이름별로 위 2~5번과 같이 구현하고 합친다. 할 일끼리 같은 파일을 고치면 순차로 한다.
3. 이번 기능 확인, 통합 테스트, 회귀 테스트를 위와 같이 한다.
   외부 서비스 준비는 새 외부 호출이 생겼을 때만 한다.
4. 커밋 메시지: "fix: 002-signup 수렴 N회차"
5. 그 회차의 할 일에 체크한다.
   spec-index.md 상태를 "converge N회차 implement 완료"로 바꾸고 커밋한다.
   다음 단계는 /meta-converge라고 알린다.
