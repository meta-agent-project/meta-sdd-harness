# meta-requirement-change

요청 하나가 어느 문서까지 바뀌는지 사용자가 말하지 않아도 찾아낸다.
문서를 고치고 다시 할 단계를 정해 두면 진행은 /meta-flow가 잇는다.

## 순서

1. 읽기
   roadmap.md, contract.md, backlog.md, issues.md, wiki/spec-index.md를 읽는다.
   요청이 닿는 기능의 spec.md, tech.md, ai/plan.md를 읽는다.
   그 기능과 데이터, 화면, 용어를 함께 쓰는 다른 기능도 읽는다. spec이 있으면 spec.md, 없으면 roadmap 줄과 backlog 항목이다.
   화면이면 design/design-system.md를 읽는다.

2. 영향 판정
   요청을 아래 판정 표에 대어 바뀌는 문서를 모두 찾는다. 한 요청이 여러 줄에 걸칠 수 있다.
   roadmap의 목표, 한 줄 설명, 용어는 바뀐 뒤 글자 그대로 읽으면 틀린 말이 될 때만 고친다.
   이미 정한 결정과 부딪히면 그 파일과 줄을 3번에서 보이고 어느 쪽인지 묻는다.
   새 결정을 따르면 옛 줄은 같은 변경에서 고친다. 두 결정을 함께 남기지 않는다.

3. 확인
   바뀔 문서, 퍼지는 기능, backlog에 적을 줄, 다시 할 단계를 5~10줄로 보이고 AskUserQuestion으로 확인받는다.
   묻는 것은 요청의 뜻과 부딪힌 결정 중 어느 쪽인지뿐이다. 어느 문서를 고칠지는 이 스킬이 정한다.
   뜻이 여럿이면 갈래마다 바뀔 문서를 붙여 보인다.
   버그면 "요구사항 변경 없음, 버그로 고침" 한 줄만 알리고 7번으로 간다.

4. 브랜치
   - 진행 중인 기능(머지하지 않은 spec 브랜치)의 변경은 그 spec 브랜치에서 한다
   - 나머지는 기본 브랜치에서 한다
   - 완료된 기능을 다시 열어야 하는데 다른 spec 브랜치가 있으면 문서를 고치지 않는다. 요청을 issues.md에 "다시 열기 대기"로 적고 멈춘다. 기능은 한 번에 하나씩 진행한다

5. 적용
   - roadmap.md, contract.md는 meta-interview의 형식을 따른다
   - spec.md는 meta-spec의 형식을 따른다. spec-index.md의 목적과 사용자 스토리도 맞춘다
   - 새 기능은 roadmap 기능 순서의 알맞은 자리에 "이름 설명: 한 줄"로 넣는다. 상세는 backlog.md에 적는다. 번호는 meta-spec이 붙인다
   - 이미 붙은 기능 번호는 바꾸지 않는다. 브랜치 spec/번호와 태그 lock/번호가 그 번호를 쓴다
   - backlog.md는 아래 형식을 따른다. 그 기능 항목이 이미 있으면 그 아래에 더한다
   - 고친 문서를 커밋한다. 커밋 메시지: "docs: {기능} 요구사항 변경"

6. 다시 할 단계
   spec이 바뀐 기능만 정한다. roadmap, backlog만 바뀌었으면 건너뛴다.

   잠금 태그 lock/{기능 번호}가 없는 기능 (tdd 전)
   - 바뀐 spec 때문에 낡은 문서를 만든 첫 단계의 앞 상태로 spec-index.md 상태를 되돌린다
   - 기술이 바뀌면 "spec 완료", 화면이 바뀌면 "tech 완료", 동작만 바뀌면 "mockup 완료"(mockup을 건너뛴 기능은 "mockup 건너뜀")
   - 지금 상태가 그보다 앞이면 그대로 둔다

   잠금 태그가 있는 기능 (tdd 후, 완료 포함)
   1. 완료된 기능이면 기본 브랜치에서 spec/{기능 번호} 브랜치를 만들고 옮긴다
   2. 기술이 바뀌면 /meta-tech, 화면이 바뀌면 /meta-mockup, 모듈이나 인터페이스가 바뀌면 /meta-plan을 이 스킬 안에서 실행해 그 문서만 고친다. 그 스킬이 안내하는 다음 단계는 따르지 않는다
   3. ai/tasks.md 5단계 끝에 "### 요구사항 변경 (YYYY-MM-DD) {한 줄 요약}"을 넣는다. meta-converge가 이 줄 뒤의 회차만 센다
   4. 상태가 "implement 완료", "converge 완료", "완료"면 "implement 완료"로 바꾼다. 그 밖이면 그대로 둔다. 남은 단계가 끝나면 meta-converge가 바뀐 spec과 코드를 비교해 할 일을 만든다
   5. 커밋한다

   진행 중인 기능의 문서가 다른 기능의 변경으로 바뀌면 그 기능도 같은 규칙으로 정한다.
   완료된 기능의 문서를 고쳤으면 converge 뒤 /meta-wiki가 다시 돈다고 알린다.

7. 버그
   문서는 맞고 코드만 다를 때다.
   진행 중인 기능이면 그 spec 브랜치에서, 아니면 기본 브랜치에서 고친다.
   1. investigate나 superpowers:systematic-debugging 스킬이 있으면 그것으로 원인을 찾는다
   2. 버그를 재현하는 테스트를 먼저 쓰고 실패를 확인한다
   3. 코드를 고친다
   4. 프로젝트 전체에 test, typecheck, lint를 실행한다
   5. issues.md에 이 버그 줄이 있으면 지운다
   6. 커밋한다. 커밋 메시지: "fix: {기능 번호} {무엇을}"
   고치다가 spec이 틀렸거나 비어 있음이 드러나면 멈추고 2번으로 돌아간다.

8. 알리기
   바뀐 문서, 되돌린 상태, 다음 단계를 알린다. 다음 단계는 /meta-flow로 이어 간다.

## 판정 표

| 무엇이 바뀌나 | 고칠 문서 |
|---|---|
| 기능 추가, 삭제, 합침, 나눔, 순서, 한 줄 설명, 나중에, 하지 않는 것 | roadmap.md |
| 목표, 사용자, 성공 기준이 바뀌는 큰 방향 전환 | 고치지 않는다. /meta-interview로 보낸다 |
| 원칙, 제약, 공통 기술, 품질 기준 | contract.md. 그 규칙을 쓰는 기능마다 아래 줄로 다시 판정한다 |
| spec이 있는 기능의 동작, 화면, 기술 | 그 spec.md. roadmap은 한 줄 설명이 틀려질 때만 |
| spec이 없는 기능의 요구사항 | backlog.md의 그 기능 항목. 한 줄 설명이 틀려지면 roadmap도 |
| 다른 기능으로 퍼짐 | spec이 있으면 그 spec.md도 같은 변경에서, 없으면 backlog.md |
| 여러 화면에 걸친 디자인 값, 컴포넌트 | 고치지 않는다. /meta-design-consistency로 보낸다 |
| 문서는 맞고 코드만 다름 | 없음. 7번 버그로 간다 |
| 요청한 것이 이미 문서에 있음 | 없음. 어디에 있는지(FR, 줄) 알리고 진짜 뜻을 묻는다 |

기술, 설계, 외부 서비스 규칙이 어느 문서에 속하는지는 .claude/meta-rules.md의 "규칙이 바뀌었을 때 고칠 문서"를 따른다.

## backlog.md 형식

```
# 백로그

## export 내보내기
- (2026-10-10) 강의 제목은 50자까지 보여준다. 002-slide-editor 변경에서 나옴
```

상세만 짧게 적는다. spec처럼 깊게 쓰지 않는다.

## issues.md 형식

```
# 이슈

## AI가 발견한 문제
- 002-signup: 가입 버튼 높이 44. src/pages/signup.css:12. 디자인 일관성 검사 중 발견

## 다시 열기 대기
- 001-lecture-store: 강의 제목 50자 제한. 002-slide-editor가 끝난 뒤 다시 연다
```
