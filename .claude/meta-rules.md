# meta 하네스 공통 규칙

meta 스킬과 에이전트는 문서를 쓰기 전에 이 파일을 읽는다.

이 파일은 하네스를 설치하거나 업데이트할 때 덮어쓴다.
프로젝트마다 다른 규칙은 contract.md에 쓴다.

## 사람이 보는 문서

대상
- roadmap.md, contract.md, design-system.md, note.md
- specs/번호/spec.md, tech.md
- wiki/ 안의 파일
- meta 스킬과 에이전트 파일

쓰는 법
- 한글로 짧게 쓴다. 한 줄에 하나만.
- 허용하는 기호는 # , - , 번호 목록(1. 2. 3.)이다.
- 표는 꼭 필요할 때만 쓴다.
- 코드 블록(```)은 예시를 보여줄 때만 쓴다.
- ** , __ , ~~ , > , 이모지, 장식 기호를 쓰지 않는다.
- 링크는 [글자](주소) 형식을 쓰지 않는다. URL만 한 줄에 쓴다.
- 해당 없는 항목은 지운다. "없음"이라고 쓰지 않는다.

## 결과를 선언하고, 방법은 정하지 않는다

문서는 "무엇이 되면 성공인가"를 선언한다. "어떻게 하라"와 "하지 마라"는 쓰지 않는다.
방법은 AI가 정한다. 선언을 만족하는지는 테스트가 확인한다. 테스트를 통과하면 성공이다.

1. "하지 마"는 "이렇게 한다"로 바꾼다
   - 예: "버튼을 회색으로 만들지 마" → design-system.md "주 버튼: 기본색 배경"
   - 예: "유료 서비스는 쓰지 마" → contract.md "무료 서비스만 쓴다"
   - 무엇으로 바꿀지 모르면 사용자에게 "그럼 어떻게 할까요?"라고 묻는다
   - 금지 목록을 만들지 않는다
2. 진짜 막아야 하는 것은 테스트로 남긴다
   - 결과로 확인할 수 있게 바꿔 테스트를 쓴다
   - 예: "비밀번호를 평문으로 저장하지 마" → 테스트 "저장된 비밀번호 값은 입력값과 다르다"
   - 테스트로 확인할 수 없는 금지는 규칙으로 남기지 않는다
3. 사용자가 "하지 마"로 피드백하면
   1의 방법으로 바꿔 원본 문서에 쓰고, 2의 방법으로 테스트를 추가하고, 코드를 고친다

## 문서가 먼저, 코드는 뒤

1. 문서에는 최신 상태만 쓴다. 변경 이력은 쓰지 않는다. 이력은 git으로 본다.
2. 문제가 생기면 코드보다 원본 문서를 먼저 고친다. 고친 문서가 선언이고, 코드는 그 선언을 따른다.
3. 커밋 메시지에 무엇을 왜 고쳤는지 쓴다.

문서를 고칠지 정하는 기준
- 이 수정 때문에 누군가 알아야 할 규칙이나 결정이 바뀌면, 그 규칙이 속한 문서를 먼저 고친다.
- 규칙은 그대로이고 구현을 실수한 것이면, 문서는 고치지 않는다. 실패하는 테스트를 먼저 쓰고 코드를 고친다. 테스트가 선언이다.
- 문서가 이미 맞게 말하는데 코드가 따르지 않은 것도 구현 실수다.
- 문서에 코드를 넣지 않는다. 문서는 규칙과 결정만 담는다.

규칙이 바뀌었을 때 고칠 문서
- 기능의 동작이 바뀜: spec.md. 사용자가 허락할 때만 고친다
- 기술이나 버전이 바뀜: tech.md, ai/research.md
- 설계나 인터페이스가 바뀜: ai/plan.md
- 가짜 응답이 실제와 다름: ai/research.md의 응답 예시
- 키 문제, 서비스 장애: 고칠 문서 없음. 환경 문제다

이미 완료된 기능의 문서를 고치면 그 기능의 wiki도 다시 갱신해야 한다. /meta-wiki를 다시 돌리라고 알린다.

## 커밋

모든 스킬은 끝날 때 바뀐 파일을 커밋한다.
메시지 형식: "{종류}: {기능} {단계}". 예: "docs: 002-signup spec"
스킬에 커밋 메시지가 따로 적혀 있으면 그것을 쓴다.

## 브랜치

spec 하나는 spec 브랜치에서 만들고 끝나면 기본 브랜치에 머지한다.
기본 브랜치는 저장소의 기본 브랜치(main 또는 master)다.

- 브랜치 이름: spec/{기능 번호}. 예: spec/002-signup
- meta-interview, meta-spec은 기본 브랜치에서 실행한다
- meta-tech가 시작할 때 spec 브랜치를 만든다. 이미 있으면 그 브랜치로 옮긴다
- meta-tech부터 meta-wiki까지는 spec 브랜치에서 실행한다
- meta-wiki가 끝나면 기본 브랜치에 머지하고 spec 브랜치를 지운다
- 머지는 --no-ff로 한다. 기능 하나의 커밋이 이력에서 한 묶음으로 보이게 한다
- 동시에 진행하는 spec 브랜치는 하나뿐이다
- 머지하지 않은 spec 브랜치가 있으면 그 기능이 진행 중인 기능이다
- meta-live는 기본 브랜치에서 실행한다

## 루프 모드

meta-worker로 실행될 때는 사용자에게 직접 묻지 않는다.
묻는 지점에서는 .meta-loop/question.md에 질문, 선택지, 추천과 이유를 쓰고 멈춘다.
형식은 .claude/agents/meta-worker.md를 따른다.

## 레인 에이전트

레인은 spec 안의 코드 모듈 하나다. 레인 에이전트는 자기 레인의 파일만 다루고, 공용 파일은 스킬이 다룬다.

테스트 (meta-tdd)
- 레인마다 테스트 에이전트를 순서대로 띄운다. 같은 폴더에서 한 번에 하나만 일한다
- 레인이 끝날 때마다 스킬이 커밋한다. 커밋 하나가 레인 하나라서 누가 무엇을 바꿨는지 정확히 보인다

구현 (meta-implement)
- 독립성이 확인된 레인만 병렬로 구현한다. 확실하지 않으면 순차로 둔다
- 구현 에이전트는 레인마다 별도 작업 폴더(worktree)와 레인 브랜치에서 일하고, 자기 레인 브랜치에 커밋한다
- 스킬이 통합 담당이다. 레인을 하나씩 spec 브랜치에 합치고 충돌을 해결한다
- 합친 뒤 통합 검증은 항상 한다

공통
1. 라이브러리 설치는 스킬이 한다. 레인 에이전트는 더 필요한 라이브러리가 있으면 필요하다고 돌려준다
2. 레인 에이전트는 자기 레인의 테스트만 실행한다. 전체 테스트, typecheck, lint는 스킬이 한다
3. 레인 에이전트는 맡은 파일만 고친다. 스킬이 레인 커밋이나 레인 브랜치의 변경 목록으로 확인하고, 범위 밖이 바뀌었으면 그 레인에 다시 맡긴다
4. 공용 파일을 고쳐야 하면 레인 에이전트는 필요하다고 돌려주고, 스킬이 그 레인을 순차로 돌린다

## 관련 없는 문제를 발견했을 때

지금 작업과 상관없는 문제를 발견하면 고치지 않는다.
- 에이전트는 "돌려줄 것"에 담아 돌려주기만 한다. note.md를 직접 고치지 않는다
- 스킬이 받아서 note.md의 "AI가 발견한 문제" 구역에 적는다
- 적는 내용: 어느 기능의 문제인지, 증상, 파일 위치, 무엇을 하다가 발견했는지

## 실행 명령

테스트, 타입 검사, 코드 규칙 검사는 항상 아래 이름으로 실행한다.
- 테스트: test
- 타입 검사: typecheck
- 코드 규칙 검사: lint

JavaScript 프로젝트는 npm run test, npm run typecheck, npm run lint로 실행한다.
다른 언어는 그 언어의 표준 위치에 같은 이름을 만들어 실행한다.
이 이름은 첫 기능의 meta-tdd 0단계에서 만든다.
